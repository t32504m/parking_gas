# 実環境での確認（ハーネスでは確かめられないこと）

ローカルのハーネスで合格しても、次の3つは本物の Google と本物の人でしか確かめられない。
ここに書いた確認が終わるまで、本番運用に入らない。

無料の Google アカウントで 1〜2章を行う手順と試験項目は、`docs/REAL_TEST_無料アカウント.md` にまとめた。

## 1. エミュレータの仮定の確認（開発の早い段階で一度）

`harness/real-gas/ASSUMPTIONS.md` の仮定が正しいかを、使い捨ての GAS プロジェクトで確かめる。

1. `harness/real-gas/FaithfulnessProbe.gs` 冒頭の手順どおりに実行する（所要 20〜30分）。
2. 結果の JSON を `harness/real-gas/results/` に保存する。
3. `node harness/real-gas/compare.js harness/real-gas/results/*.json` を実行し、「★不一致」が無いか見る。
4. 不一致があれば、実装AIにエミュレータの修正を依頼する（人が内容を確認してから `npm run harness:seal`）。
5. 所要時間の実測値で `harness/emulator/cost-model.json` を更新し、`"calibrated": true` にする。

## 2. 本番に近い環境での動作確認（実装の区切りごと）

検証用のスプレッドシートと GAS プロジェクトを別に作り（本番・検証・デモを分ける：要件7.2）、`docs/SETUP.md` の手順で公開する。

- [ ] 利用者として、スマートフォン（iPhone・Android 各1台）で予約→確定表示→予約番号を確認
- [ ] 2台のスマートフォンで、残り1台のコマに同時に申し込み、確定が1件だけになる
- [ ] 管理者として、電話受付の代行登録（メールなし）→確定表示
- [ ] 管理者として取消し→利用者画面で残り台数が戻る
- [ ] 管理者の資格の無いアカウント（別の Google アカウント・未ログイン）で管理者用 URL を開き、台帳の情報が見えない
- [ ] 機内モードを使って送信直後に通信を切り、復帰後に結果を確かめられる・二重予約にならない
- [ ] 通知メールが届く。受信までの時間を記録する（GAS の送信完了時間とは別：要件11）
- [ ] 時間主導トリガー（通知処理）が動き、失敗分が再送される
- [ ] スプレッドシートを開き、管理者がセルを直接直す必要が無いことを確認する
- [ ] 空き表示・申込み・確定の所要時間を実測し、`contract/perf-budget.json` の合格基準を人が決める
- [ ] 台帳に過去の予約を 0年分・1年分（約2,900行）・3年分（約8,800行）入れて、電話の登録1件・住民の空き状況・電話連絡の一覧の時間を測る（エミュレータでの計測は `node tools/measure-growth.js`。D-022）。結果を見て、台帳の構成（古い行の保管・読む範囲を絞る・月ごとのシート）を決める
- [ ] 予約まで試すときは、RULES の `residentBooking` と `residentLookup` を `true` にする。試験が終わったら `false` に戻す
- [ ] URL が変わらないこと：既存のデプロイを「新バージョン」に更新しても、前の版に戻しても、同じ URL で開けること。「アクセスできるユーザー」を変えたときに URL が変わるかも確かめる（検討資料 7章）
- [ ] 予約の変更（D-024）：同じコマに空きが1台しかないとき、2人の管理者がそこへ同時に変更・登録しても、1件しか入らないこと
- [ ] 保管（D-023）：古い予約を入れた台帳で `job_archiveLedger` をエディタから実行し、所要時間を記録する。保管の最中に住民の画面・管理者の登録を操作し、待たされても重複・消失が無いこと。翌日、トリガーが夜中に動いた記録（操作履歴の「保管」）があること
- [ ] 予約表の作り直し（D-025）：管理者が登録・取消しをした後、その月の「予約表 2026年○月」のシートで、値が変わり、日付の結合・罫線・列の幅が崩れていないこと。「スプレッドシートに書き出す」で書式をかけ直せること
- [ ] 書式の呼び出しの重さ（D-025）：エミュレータは結合・罫線などの書式の呼び出しを数えない。初めての月の予約表を作る登録（約45回の書式の呼び出し）と、2回目以降の登録の所要時間を比べる
- [ ] 予約の確認の数え上げのロック（D-029 の仮定 X-01）：`residentLookup` を開けた検証の環境で、2つのブラウザ（別のアカウントと未ログイン）から予約の確認を同時に送り、片方が待つこと。同じ間に、管理者の登録が待たずに終わること
- [ ] 文字が丸ゴシック（Zen Maru Gothic）で出るか。GAS の画面から Google Fonts を読み込めない場合でも、iPhone（ヒラギノ丸ゴ）・Windows（BIZ UDPゴシック、游ゴシック）・Android（Noto Sans CJK JP）の**日本語の字形**で出ること（中国語の字形にならないこと）を、実機で確かめる。

## 3. 人による使いやすさの確認（ペルソナ評価の裏づけ）

ペルソナ評価はAIによる予測。実際の住民・管理者で確かめる。

- [ ] 高齢の住民1〜2名に、何も説明せずに `personas/personas.json` と同じ課題をやってもらい、横で見る（手を出さない）
- [ ] 管理者（駐車場係）に、電話を受けている想定で代行登録・取消しをやってもらう
- [ ] つまずいた場面・言われた言葉を記録し、ペルソナ評価の予測と比べる
- [ ] 予測が外れた点は `personas/personas.json` の人物像・制約に反映する（人が行い、`npm run harness:seal`）

## 4. 運用ルールの決定（要件13章）

`contract/provisional-rules.json` の各項目を自治会で決め、決まったら値と `status` を更新する。特に：

- [ ] 予約方式（先着順を正式に採用するか）と、先着の基準
- [ ] 管理者の本人確認方式（Google アカウント／パスコード等）と公開設定（`appsscript.json` の `webapp`）
- [ ] 一般利用者の取消し・変更の方法と本人確認
- [ ] 電子台帳が使えない間の受付（障害時）
