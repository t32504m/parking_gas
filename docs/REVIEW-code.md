レビュー担当が `src/` を先入観なく読み、問題を挙げて直した記録。
測り方：

- `node tools/measure-ops.js` … 公開の関数ごとに、シートを呼んだ回数（エミュレータの `metrics.ops` のうち `sh.*`・`ss.*`）と推定時間（`estGasMs`）。過去の予約が 0日分と 365日分（2920行）の台帳で同じ操作を流し、回数が行数で増えるかを見る。

## 3. 直さないこと（理由）

| ID | 理由 |
|---|---|
| P-9 | 予約番号の重複よけには、保管の予約番号の全てが要る。読むのは2列だけ（`archiveKeys_`）で、シートを呼ぶ回数は行数で増えない（2回）。読む量は保管の行数で増えるが、1年で約3,000行×2列で小さい。番号の作り方（連番など）を変えると、電話口の運用が変わるので変えない |
| D-11 | 一覧（オンライン・電話・窓口）と予約表（ネット・電話・窓口）で、見せる文字がわざと違う（予約表は管理者の Excel に合わせた。D-017）。まとめると、どちらかの文言が変わる |
| C-3 | 変更の「新しい枠を足す」と「古い枠を放す」は、1回の書込みにはできない（足すのは行の追加、放すのは別の行の書換え）。間で実行が止まると、1つの予約が2つの枠を持つ（空きが1台分少なく見える。予約は消えない）。直すには、止まった実行の残骸を見つけて片付ける仕組み（BUG-001 の「残ること」と同じ）が要る。別の作業として依頼者と決める → 依頼者の考えにもとづき直した（D-026） |
| 長い関数 | `book_`（約60行）・`adminChange_`（約55行）・`availability_`（約40行）は、上の共通化で短くした。これ以上分けると、ロックの中の手順（読む→判定→書く）の順番が読み取りにくくなるので分けない。`Admin.html` の `bindPanel`（約95行）は、作業の枠ごとの短い登録の並びで、分けても行が移るだけなので分けない |
| 書式の呼び出し | エミュレータが数えないので、表の「推定」には入らない。予約表の書式は、シートを作るときと書き出すときだけ（約45回）にした。本物の GAS で時間を測る（`docs/REAL_ENV_CHECKLIST.md`） |
| シートを探す（`ss.meta`） | 登録1回で7回（予約・割当て・使用禁止・予約（保管）・通知・操作履歴・予約表）。シートごとに1回で、行数では増えない。`getSheets()` で1回にする形は、エミュレータでは名前を聞くたびに呼び出しになり、かえって増えるので採らなかった。本物の GAS での重さは実測で確かめる |
| 保管（`job_archiveLedger`） | シートを呼ぶ回数は 37〜43回。違いは「保管のシートに行が足りないときに行を足す」の有無で、行数に比例しない（上限がある） |
| BUGS.md Q-3〜Q-5 | 依頼者に確かめること（今の動きは仕様の範囲）。レビューでは変えない |
