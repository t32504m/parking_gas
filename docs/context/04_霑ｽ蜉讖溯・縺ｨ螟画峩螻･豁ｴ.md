# 追加した機能と変更の履歴

元の要件定義（`docs/REQUIREMENTS.md`）に書かれていなかったが、開発の中で追加した機能と、その理由をまとめる。
後半は、開発の経過（いつ・何が見つかり・どう直したか）。

---

## 1. 追加した機能（製品＝`src/`）

| 機能 | 内容 | 追加した理由 |
|---|---|---|
| 予約番号による確認 | 予約番号＋電話番号の下4けたで、自分の予約の日時・台数・料金・状態を確かめる（氏名は返さない） | U-08「後から確認する方法」の具体化。Google ログインなしで本人に近い確認をするため（仮） |
| 6けたの数字の予約番号 | 英字を使わない | 電話口で読み上げやすく、高齢の方が書き写しやすい |
| 満車のときの案内 | 満車の時間帯について「同じ時間帯が空いている近い日」をボタンで示し、相談先を出す | ペルソナ評価1回目：78歳の住民が「満車のとき、どうすればよいか分からない」（重めの不満） |
| 相談先の設定 | スクリプトプロパティ `CONTACT_NOTE`（例：駐車場係の名前と電話番号）を画面の案内に出す | ペルソナ評価2回目：「電話でご相談くださいとあるのに番号が無い」 |
| カレンダーの「今日の週から」表示 | 今月は、今日より前の週を出さない | 1回目：管理者・住民ともに「押せない日が並び、目的の日まで長くスクロール」 |
| 一部満車の表示 | 日の記号を「△ 満車の時間帯あり」にする | 2回目：「夜だけ満車の日が『空きあり』のまま」 |
| 結果が分からないときの扱い | 「結果が分かりませんでした」と申し込んだ内容を出し、「結果を確かめる」で確定・不成立・未着を判定。未着なら同じ内容でもう一度申し込める（二重にならない） | 要件6.5の通信断の扱いを、利用者の操作として具体化 |
| 確認画面の注意書き | 「押したあと通信が切れたら、押し直さずに結果を確かめる」 | 1回目：電波の弱い住民「先に知りたい」 |
| 完了画面の要約 | 日時・台数・料金をお知らせの枠に一行で出し、「この予約は1件だけ登録されています」と明記 | 1〜2回目：「確定画面で日時がスクロールしないと見えない」「1件だけか不安」 |
| 管理者の結果画面の読み上げ文 | 「予約番号は 4 8 2 9 1 5 です」と1けたずつ区切った文を出す | 電話口で伝える場面に合わせた |
| 取消し画面の改善 | 予約の見出しを「名前＋受付方法」にし、ボタンを「〇〇さんの予約を取り消す」にした。理由はボタンで選べ、取消し後は結果の表示へ自動で移動 | 1回目：管理者「同じ文言のボタンが並んで迷う」「取れたか見えない」 |
| 管理者の日付選択 | 日付の入力欄ではなく「10月25日（日）」の選択肢にした。時間帯でも絞れる | 1回目：「今日が入っていて直し方が分かりにくい」 |
| 管理者メニューの折りたたみ | 作業中は「← メニューに戻る」だけにして画面を短くした | 画面の長さの指摘 |
| 電話連絡の一覧 | 電話受付の予約と、メールが届かなかった予約をまとめ、「電話しました」で対応者と日時を残す | A-07 の具体化 |
| 日ごとの一覧（印刷） | 時間帯ごとに駐車場番号・氏名・部屋・電話・予約番号を並べ、印刷用の表示にする | A-09 の具体化（CSV出力の代わり） |
| 管理者の確認の改善 | パスコードの前後の空白・改行を無視する。5回続けて間違えて止まっているときは「しばらく確認できません」と区別して表示する | 利用者から「管理者画面に入れなかった」との報告（2026-10-19） |

## 2. 追加した機能（手元確認・検証の道具＝`harness/`）

| 機能 | 内容 |
|---|---|
| GAS の再現環境 | SpreadsheetApp・LockService・Session・MailApp・HtmlService などを Node 上で再現。各実行を別スレッドで並行させ、競合を実際に起こす |
| 実GASの落とし穴の再現 | 文字列の自動変換（電話番号の先頭0が消える等）、戻り値の Date が null、`_` で終わる関数は呼べない、公開設定で利用者のメールが取れない、書込みの遅延反映（flush の必要性） |
| 受入試験35件と台帳の不変条件 | 要件11の正常・競合・境界・障害。毎試験後に台帳を直接読み、二重予約などを検査 |
| 静的検査 | GAS で動かない書き方、未宣言の公開関数、同名関数、viewport の付け忘れ |
| 画面の自動監査 | スマホ幅での横スクロール・文字の大きさ・押しやすさ・コントラスト |
| ペルソナ評価 | 5人の利用者像を、実装と別のAIが画面操作して評価する。達成は台帳で客観判定する |
| 自己試験 | わざと壊した実装14種を、試験が全て見抜けるかを確かめる |
| 保護ファイルの封印 | 試験・合格基準・ハーネスの改変を検出する |
| 実環境プローブ | 本物の GAS で動かして、再現の仮定が正しいかを照合する |
| 手元確認用の起動 `npm run serve` | 画面を PC で触る。固定パスコード、確認なしで管理者画面に入る入口（`/__harness/admin-auto`）、台帳と送ったメールを見るページ（`/__harness/ledger`）。いずれも GAS には含まれない |

## 3. 開発の経過

| 時期 | 出来事 |
|---|---|
| 着手 | 要件定義を受け取る。Google のサービスに接続できない環境のため、先に検証基盤（ハーネス）を作る方針にした |
| ハーネス作成 | GAS の再現環境・受入試験・静的検査・画面監査・ペルソナ評価・自己試験を作る。最小実装で全試験が合格でき、わざと壊した実装を全て見抜けることを確認した |
| 依頼の追加 | 「ペルソナが一定以上満足するまでという評価も加えたい」→ ペルソナ評価を追加。自己採点で甘くならないよう、評価役は別のAIにして、台帳での客観判定と組み合わせた |
| 実装開始 | 「このハーネスで実装ループを回す。UI はデジタル庁のデザインシステム」→ 公式デザイントークンを同梱 |
| サーバー実装 | 受入試験35件に合格。途中、ハーネスが「ファイルの読込順に依存した定義」を検出（本物の GAS でも起きる問題）→ 関数にして解消 |
| 画面実装 | 利用者・管理者画面と画面試験11件。合格 |
| ペルソナ評価 1回目（r1） | 評価役の起動が API 側の安全判定で止まったため、別のモデルで実施。主観で重めの不満が複数あった（満車の案内なし、過去の週が長い、取消し結果が見えない、「スクリーンショット」が通じない）。客観判定が全員「未達成」と出たが、ハーネスの不具合（HX-001）と判明 |
| 改善 | 満車の案内、カレンダー、完了画面、取消し画面、日付の選択肢などを直した |
| ペルソナ評価 2回目（r2） | 主観は重めの不満1件（相談先の電話番号なし）まで改善。客観判定は、常駐プロセスが古いコードのままだった不具合（HX-002）で再び無効 |
| 改善 | 相談先の設定、一部満車の表示、通信断の画面に申込み内容。ハーネスは版の自動更新と、判定結果を評価役から隠す修正 |
| ペルソナ評価 3回目（r3） | 5人全員合格。`verify:strict` 合格で完成とした。仕様書 `docs/SPECIFICATION.md` を作成 |
| 手元での確認 | 「GAS に移す前に手元で試したい」→ `npm run serve` の使い方を案内 |
| 管理者画面に入れない報告 | 起動表示の分かりにくさ（メールアドレスが記号化されたURLの中だけ、毎回変わる24桁のパスコード）と、パスコードの前後の空白・停止中の表示を改善（HX-004、D-009）。「テストなので確認を消してよい」との意見を受け、本番の確認は残し、手元確認用の起動にだけ確認なしの入口を追加 |
| ペルソナ評価 4回目（r4） | 画面を変えたため再評価。5人全員合格。`verify:strict` 合格 |
| UI・UX の指摘 | 「UI と UX が悪い。管理者画面は一覧性が悪く、直観的でない」「見た目が AI の作ったような形でないのは良いが、見にくい所がある。デジタル庁にこだわらなくてよい」「手数より分かりにくさが問題。ただし文や注釈を足してほしいわけではない」→ 問題の洗い出しと仮説（`docs/UX_AUDIT.md`） |
| 画面の作り直し | 管理者：1週間の予約表を最初の画面にし、枠を押して登録・詳細・取消し（D-010、D-011）。利用者：空き状況の表を最初の画面にし、枠を押して申し込む。デザイントークンを外し、独自の配色に |
| 評価の穴をふさぐ（HX-005） | 画面監査に PC 幅、PC の管理者ペルソナ、主観評価に「見通し」（4以上で合格）を追加 |
| ペルソナ評価 r5 | 評価役どうしのセッション取り違えが判明し無効（HX-006）。指摘から、満車の行き止まり、スマホで予約番号が隠れる、電話で伝えた予約の扱い（D-012）、取消し理由の表示、スマホの日付ボタンを直した |
| ペルソナ評価 r6〜r8 | 見通し3の課題が残る → スマホでは枠だけをページとして出す、管理者のスマホの操作列の並べ替え、満車時の電話ボタン。r8 で横はみ出しの退行が見つかり直した |
| ペルソナ評価 r9 | 6人全員合格。`verify:strict`・自己試験とも合格 |
| 見た目の作り直し | 「文字は Shift_JIS の範囲で。中国フォントが多すぎる」「やはり UI が良くない」→ 気になる点を4つとも確認し、方向は「やわらかく親しみやすく、AI らしくしない」。丸ゴシック、○△×、空きは静かに、枠線をやめる、芝の緑・山吹・えんじ（D-013）。ペルソナ評価は利用者の指示で行わない |

## 4. ハーネスの修正記録（詳細は `docs/DECISIONS.md`）

| 番号 | 内容 | 判定への影響 |
|---|---|---|
| HX-001 | ペルソナ課題の達成判定が、台帳の状態名（確定）を英語の状態名と比べていた | 正しく見つけるようにしただけで、甘くはしていない |
| HX-002 | 操作ツールの常駐プロセスが古いコードのまま動き続けた。判定結果を評価役が読むログから分けた | 同上 |
| HX-003 | 評価役に見せる選択欄の値が内部の値（S3 等）だった | 実装には影響しない |
| HX-004 | 手元確認用の起動の改善（表示・固定パスコード・台帳ページ・確認なしの入口） | 試験の判定には影響しない |
| HX-005 | PC 幅の監査、PC の管理者ペルソナ、見通しの点数を追加（利用者の指摘による） | 合格基準を厳しくした |
| HX-006 | 並行評価でのセッション取り違えを防ぐため、セッションIDを推測できない形に | 判定の基準は変えていない |

## 5. 実装での決定（詳細は `docs/DECISIONS.md`）

| 番号 | 決定 | 区分 |
|---|---|---|
| D-001 | 管理者の確認はメールアドレス＋パスコード（ハッシュ保存、6時間有効、5回で15分停止） | 仮 |
| D-002 | 公開は「自分として実行・全員」。住民はログイン不要 | 仮 |
| D-003 | 台帳は予約・割当て・通知・操作履歴の4シート。見出しと状態は日本語 | 決定 |
| D-004 | 予約番号は6けたの数字 | 決定 |
| D-005 | 利用者の確認は予約番号＋電話番号の下4けた。利用者の取消しは未実装 | 仮 |
| D-006 | 不成立の申込みも台帳に残す（所在不明0） | 決定 |
| D-007 | 通知は5分ごとのトリガー。失敗は再送待ち | 決定 |
| D-008 | 画面はデジタル庁デザインシステムのトークンに沿う。記号を見せず、色だけに頼らない | D-010 で置き換え |
| D-009 | パスコードの前後の空白を無視し、停止中は区別して表示 | 決定 |
| D-010 | 画面の作り直し：最初の画面を表にし、枠を押して操作する。説明文で補わない。独自の配色 | 決定 |
| D-011 | 管理者が押した区画（例：93番）が空いていれば、そこに割り当てる | 決定 |
| D-012 | メールの無い予約は、登録後の「本人に伝えた」で電話連絡を済みにできる | 決定 |
