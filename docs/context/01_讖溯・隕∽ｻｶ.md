# 機能要件と実装状況

- 基準日：2026年10月19日
- 元資料：`docs/REQUIREMENTS.md`（自治会駐車場予約システム 基本実装に向けた要件定義・開発引継ぎ）
- 状態の記号：**済**＝実装し、自動試験で確認済み／**仮**＝実装済みだが、運用ルールが未決定のため仮の方式／**未**＝未実装

---

## 1. 目的（要件1章）

自治会の駐車場予約を、住民と非エンジニアの管理者が分かりやすく使える仕組みにする。
オンライン申込みに加えて、電話・対面などのアナログ受付も併用する。アナログで受けた申込みは、管理者がスマートフォンからその都度登録する。
受付経路にかかわらず、予約を共通の台帳で管理し、二重予約や受付漏れを防ぐ。

## 7. アナログ受付との連携（要件6.3）

| 要件 | 対応 |
|---|---|

## 8. 予約台帳（要件6.4）

回答の記録（予約）と、実際に確保した駐車枠（割当て）を分けている。

| 分類 | 要件の項目 | 台帳の列 |
|---|---|---|
| 識別 | 予約ID、受付要求ID | 予約番号、受付要求ID |
| 利用日時 | 利用日、コマID、開始・終了日時 | 利用日（年つき）、コマID、時間帯、開始日時、終了日時 |
| 割当て | 駐車場番号、台数 | 割当てシートの駐車場、予約の台数 |
| 利用者 | 氏名、棟、部屋番号、連絡先 | 氏名、棟、部屋番号、電話番号、メール |
| 受付 | 経路 | 受付経路（ONLINE／PHONE／COUNTER） |
| 時刻 | システム受付・確定・更新、電話等の受付日時 | 受付日時、確定日時、更新日時、電話等の受付日時 |
| 状態 | 受付済み・確定・不成立・取消済み | 状態（受付中／確定／不成立／取消済み）、不成立理由 |
| 金額 | 適用料金、料金区分 | 料金合計、コマID（料金はコマIDから決まる） |
| 連絡 | 連絡方法、通知状況、対応済み日時 | 連絡方法、通知シート（状態・試行回数・電話対応者・電話対応日時） |
| 管理 | 操作者、変更理由、備考 | 登録者、操作履歴シート、備考 |

## 9. 予約確定と競合処理（要件6.5）

| 要件 | 対応 |
|---|---|
| 空き表示だけで確定を判断しない | 済：確定時にロックの中で台帳を読み直す |
| 空き確認から枠の記録までを共通の排他制御に入れる | 済：スクリプトロック。flush してから解放 |
| 管理者の登録も同じ制御を通す | 済 |
| 同じ受付要求の再送で重複登録しない | 済：受付要求IDで照合 |
| 処理できなかったときに成功と表示しない | 済：ロック失敗・書込み失敗は ERROR |
| 通信が切れたら受付要求IDで結果を再確認できる | 済：`api_getRequestStatus` と「結果を確かめる」 |
| 複数台は一部確定か全部そろう場合のみかを明確にする | 仮：全部そろう場合のみ（設定で変更可） |
| 先着順では「申込み時刻順」と「確保できた順」を混同しない | 仮：「確保できた順」と明記。厳密な受付順の仕組みは未 |
