# 非機能要件と満たし方

- 基準日：2026年10月19日
- 元資料：`docs/REQUIREMENTS.md` 8章（元資料では「非用件」と書かれていたものを、非機能要件として整理）
- 「根拠」は、ハーネスの自動試験・自動監査・ペルソナ評価のどれで確かめたかを示す。ハーネスはローカルの再現環境なので、本物の Google での確認（`docs/REAL_ENV_CHECKLIST.md`）は別に必要。

## 1. 一覧

| 分類 | 要件（元資料） | 満たし方 | 根拠 | 残っていること |
|---|---|---|---|---|
| 操作性 | 非エンジニアが説明を読み込まずに基本操作を行える | 手順を4段階（日付と時間→お名前など→確認→完了）に分け、各画面で次にすることを1文で示す。英語・記号（S1、ID、エラー等）を画面に出さない | ペルソナ評価：78歳の住民・67歳の管理者を含む5人が全課題を達成し、満足度4以上 | 実際の住民・管理者による確認 |
| スマートフォン対応 | 横スクロールに依存せず、日付選択・登録・取消しを行える | 幅320pxでも横にはみ出さない配置。押せる部品は44px四方以上、ボタンは高さ56px。viewport は `addMetaTag` で設定 | 画面の自動監査（iPhone SE・Pixel 7）、画面試験 UI-01〜12 | 実機での確認 |
| 表示 | 空き・満車・確定・未確定を、色だけでなく文字でも示す | カレンダーは ○△×－ と読み上げ用の文字、時間帯は「空き 2台／満車／受付終了」、結果は見出しと文で示す | 画面試験 UI-03、色覚の特性があるペルソナ（白黒表示で評価）が合格 | － |
| 性能 | 空き表示・受付・確定・通知の所要時間を個別に測定できる | 試験で推定時間（シート操作の回数×単価）とロック待ちを記録する | 受入試験08、`reports/latest.md` の計測表 | 単価は仮。合格基準（`contract/perf-budget.json`）が未確定 |
| 安定性 | 同時申込み・再送・処理途中の失敗で、重複や受付漏れを起こさない | スクリプトロックの中で台帳を読み直して判定する。flush してから解放する。受付要求IDで再送を照合する。書く順序を「受付中→枠確保→確定」にする | 受入試験02〜04（残り1台への5人同時、管理者との競合、連打、書込み失敗、強制終了）。毎試験後に台帳の不変条件を直接検査 | 実機2台での同時申込み |
| 復旧性 | 中断した予約・通知の状態を把握し、安全に再開できる | 途中で止まった予約（受付中）は、同じ受付要求の再送で枠を片付けてやり直す。送信中のまま止まった通知は、10分後に再送待ちへ戻す | 受入試験04（書込み失敗・強制終了の後の再送） | 受付中のまま放置された予約を自動で片付ける仕組みは無い（再送されなければ枠が残る） |
| 整合性 | 利用者画面・管理者画面・台帳で同じ確定情報を参照する | どの画面も同じ台帳を読み、確定は同じ処理だけが書く | 受入試験01（オンラインと代行登録が同じ一覧・同じ残り台数） | － |
| セキュリティ | 管理者操作をサーバー側で認可する。画面の切替だけを認証にしない | すべての管理者用関数の先頭でサーバー側の確認を行う。誰でも呼べる関数はすべて権限区分を宣言し、静的検査で漏れを検出する | 受入試験06（匿名・一般利用者が管理者用関数を直接呼んでも何も変わらない）、画面試験 UI-09 | 管理者の確認方式は仮（パスコード） |
| 個人情報保護 | 一般公開の空き画面に氏名・部屋・連絡先を返さない | 空き情報の応答は台数と時刻だけ。予約の確認でも氏名は返さない | 受入試験01（応答に個人情報が含まれないかを文字列で検査） | － |
| 監査性 | 管理者が誰の予約をどう変更したか追跡できる | 操作履歴シートに日時・操作・操作者（名前とメール）・予約番号・理由を残す。予約にも登録者を残す | 受入試験06 | 変更機能が無いため、変更の履歴は未対象 |
| 保守性 | 料金・コマ・予約期間などを変更しやすくする | コマと料金は `Config.gs` の定数1か所。運用ルールはスクリプトプロパティ `RULES`。駐車場の割当て規則は `chooseSpaces_()` に分離 | コードの構成 | 料金の変更履歴（いつから何円か）は扱っていない |
| 継続運用 | 担当者交代時の所有権・権限・公開方法・バックアップを引き継げる | 手順を `docs/SETUP.md` に記載 | 文書 | バックアップの自動化は無い |
| 費用・制限 | GAS やメールの利用上限を考慮し、超過時に未処理を把握できる | 送信前に残り通数を確認し、超過分は再送待ちとして残し、管理者の一覧に出す | 受入試験07（上限2通の状態で4件） | － |

元資料の目標：**重複確定・受付済み申込みの所在不明・無断の結果変更は0件**
- 重複確定：毎試験後の不変条件検査で0件。
- 所在不明：不成立も台帳に残し、受付要求IDで後から確認できる（受入試験03）。
- 無断の結果変更：通知の失敗や再送で予約の状態を変えない（受入試験07）。取消しは管理者だけが理由つきで行い、履歴に残る。

## 2. 画面の品質基準

2026-10-19 の作り直しで、デジタル庁デザインシステムのトークンは使わなくなった（利用者の判断）。基準は次のとおり。

| 項目 | 基準 |
|---|---|
| 分かりやすさ | 説明文や注釈を増やさず、画面の形（表）と、その場で押す操作で分かるようにする |
| 文字 | 本文16px以上（12px未満は監査で不合格） |
| 押せる部品 | 44px四方以上 |
| コントラスト | 文字と背景で 4.5:1 以上（大きい文字は 3:1） |
| 色 | 色だけに頼らない（「空き3」「満車」「－」、選んだボタンの ✓） |
| 画面幅 | iPhone SE（320px）〜PC（1280px）で横スクロールなし |
| 言葉 | 利用者に英語・記号・カタカナ語を出さない |
| 文字の範囲 | Shift_JIS の範囲（`tests/impl/charset.test.js`）。日本語フォントだけを指定（丸ゴシック → UDゴシック → ゴシック） |
| 見た目 | 枠線で囲まない。主の操作だけ塗り。空きは静かに、予約・満車・選んだ所だけ目立たせる（D-013） |

## 3. ペルソナ評価の合格基準（`personas/thresholds.json`）

| 区分 | 基準 |
|---|---|
| 客観 | 課題を達成（台帳で判定）、手数が上限以内、読めない文字・押しにくい部品・横スクロール・通じない言葉が0、台帳の不変条件違反が0 |
| 主観 | 課題ごとの満足度と結果への確信が4以上、総合満足度が4以上、致命的な不満0、重めの不満は1人1件まで |
| 進め方 | 評価役は実装と別の新しいAI。不満には根拠の手番号が必須 |

2026-10-19 に「見通し（一覧性）」を加えた：課題ごとに4以上（`minTaskOverview`）。説明を読まずに、どこが空いていてどこが埋まっているかをつかめたか。

## 4. 測定する時間（要件11章）と現状

| 指標 | 測り方 | 現状（推定・エミュレータ上） |
|---|---|---|
| 空き表示時間 | 1か月分の空き取得のシート操作回数×単価 | 4回、約0.3秒 |
| 受付待ち・ロック待ち | ロック取得までの待ち時間 | 同時10件で最大 約1.4秒 |
| 確定処理時間 | 申込み1件のシート操作回数×単価 | 15回、約1.2秒 |
| 利用者の待ち時間 | 確定処理＋`google.script.run` 1往復（仮700ms） | 約2秒 |
| 通知時間 | 通知処理の推定時間 | 3件で約3.5秒 |

単価はすべて仮の値です。実環境プローブ（`harness/real-gas/FaithfulnessProbe.gs`）の実測で校正してから、合格基準を決めます。
