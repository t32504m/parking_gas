## BUG-001 登録の途中の失敗で、見えない予約が枠をふさぐ（直った）

- 確認：2026-11-09 21:30、レビュー担当の修正（src/Booking.gs ほか 21:28〜21:29）の後に S-167 を流して通った。書込み3回目で失敗させても、割当ては「解放」になり、住民の空き状況の残りは 2 のまま。同じ受付要求ID の送り直しでも確定できる（S-053）。

- 残ること：実行そのものが止まった場合（時間切れなど。`terminateAfterWrite`）は、戻す処理も動かないので、「受付中」と割当てが残る。これは同じ受付要求ID の送り直しで直る（S-053）。止まった実行の残骸を自動で片付ける仕組みは、まだ無い（docs/REVIEW-code.md 3章）。

- 試験：`[S-167] 書込みがどこで失敗しても、応答と台帳が食い違わない`（`tests/spec/11_table.test.js`）
- 再現手順：

  2. その実行の3回目のシートへの書込みで失敗させる（エミュレータ `host.setFaults({ sheetWrite: { fn: 'api_admin_register', failAt: 3 } })`。本物では「Service Spreadsheets timed out」などの一時的な失敗に当たる）。
  3. 応答は「処理できませんでした」（ERROR）。
  4. その後、同じ受付要求ID で送り直さない（管理者が画面を閉じた、別の端末だった、など）。
- 期待：
  - 失敗した登録は、枠を持たない（確定していない予約が有効な割当てを持たない）。または、確定まで済ませる。
  - どちらにしても、管理者の画面で見えて、扱える。
- 実際：
  - 予約シートに状態「受付中」の行、割当てシートに「有効」の行が残る（`ALLOC_FOR_UNCONFIRMED`：予約 xxxxxx（状態 受付中）に有効な割当てが残っている）。

  - 同じ受付要求ID で送り直すと確定になり、直る（S-053 は通る）。送り直さない限り、ずっと残る。
  - 失敗の場所によっては（書込み4・5回目）、応答は ERROR だが台帳では確定になる。これは「結果が分からない」の扱いで、受付要求ID で確かめると確定と分かるので、仕様の範囲と考える。
- 根拠：REQ 8「安定性：処理途中の失敗で重複や受付漏れを起こさない」「復旧性：中断した予約・通知の状態を把握し、安全に再開できる」「整合性：利用者画面、管理者画面、台帳で同じ確定情報を参照する」。受入試験と同じ不変条件（`harness/invariants.js` の ALLOC_FOR_UNCONFIRMED）に反する。
