# 自治会駐車場予約システム 仕様書（完成時点）

- 版：0.1.0（2026年10月19日）
- 位置付け：要件定義（`docs/REQUIREMENTS.md`）の第1段階を実装し、ハーネスによる全検証に合格した版。本番運用の前に、実環境での確認（`docs/REAL_ENV_CHECKLIST.md`）と未決定ルールの決定が必要。

## 1. 目的と範囲

住民と非エンジニアの管理者が分かりやすく使える駐車場予約の仕組みを、Google Apps Script（GAS）の Web アプリとスプレッドシートで作る。オンライン申込みと、電話・窓口での代行登録を、**同じ台帳・同じ空き判定・同じ確定処理**で扱い、二重予約や受付漏れを防ぐ。

### 実装した範囲

| 区分 | 内容 | 状態 |
|---|---|---|
| 第1段階 | 空き表示、利用者の申込み、管理者の代行登録、共通台帳への確定、予約一覧、取消し、競合・再送対策、時刻とエラーの記録 | 実装・検証済み |
| 第2段階（一部） | 管理者の確認と権限、電話連絡の管理、検索、日ごとの一覧（印刷）、通知の再送、予約番号による確認 | 実装・検証済み（方式は仮） |
| 未実装 | 利用者自身による取消し・変更（U-09）、特別予約（A-10）、全日・複数コマ、繰り返し予約、抽選・待機リスト、料金集計 | 運用ルール未決定のため |

## 2. 駐車場・時間帯・料金

| 項目 | 内容 |
|---|---|
| 駐車場 | 91・92・93 の3台（各棟共通） |
| 朝（S1） | 8:00〜11:00　1台 300円 |
| 昼（S2） | 11:00〜14:00　1台 300円 |
| 午後（S3） | 14:00〜17:00　1台 300円 |

- コマは固定ID（S1〜S4）で管理し、料金は表示名と切り離している。

## 4. 画面

2026年10月19日に、利用者の指摘（「一覧性が悪い」「直観的でない」「分かりにくい」）を受けて作り直した（経緯と仮説は `docs/UX_AUDIT.md`）。

- **説明文や注釈を増やさず、画面の形と操作で分かるようにする。** 最初の画面を「表」にし、表の枠を直接押して操作する。
- 見た目は「やわらかく、しかし静か」。文字は丸ゴシック（Zen Maru Gothic。読めなければ端末の丸ゴシック・UDゴシック）。色は芝の緑（操作）・山吹（今日・選んだ所）・えんじ（満車）。枠線で囲まず、主の操作だけを塗りのボタンにする（D-013）。
- 空いている所は静かに、予約・満車・選んだ所だけが浮かび上がる。
- 文字は Shift_JIS の範囲に限る。日本語フォントだけを指定し、中国語の字形に落ちないようにする。
- 本文16px以上。押せる部品は44px四方以上。選んだボタンには、線で描いたチェックが付く。
- 空き・満車・受付時間外は、色だけでなく記号と文字（○3台・△1台・×満車・網かけ）で示す。
- 横スクロールは発生しない（iPhone SE 幅 320px、PC 幅 1280px で確認）。
- スマホでは、枠を押すと入力や結果が**画面全体**に出る（スクロールは1つだけ）。閉じると表の同じ位置に戻る。PC では表の右に出る。

## 5. 処理の仕様

### 5.1 予約の確定（オンライン・代行登録で共通）

1. サーバー側で入力を検査する（日付の実在、コマID、台数の範囲、必須項目、電話・メールの形式、文字数）。
2. スクリプトロックを取得する（最大15秒）。取れなければ「混み合っています」を返し、何も書かない。
3. 同じ受付要求IDの予約があれば、その結果を返す（再送対策）。前回が途中で止まっていた場合は、残っている枠を解放してからやり直す。
4. ロックの中で台帳を読み直し、規則（過去日・締切・受付期間）と空きを判定する。
5. 次の順で台帳に書く。途中で止まっても安全な順序にしている。
   1. 予約行を「受付中」で書く
   2. 駐車枠を「有効」で確保する
   3. 予約行を「確定」にする
   4. 通知行を書く
   5. 代行登録なら操作履歴を書く
6. `SpreadsheetApp.flush()` してからロックを解放する。

不成立（満車・締切など）の申込みも「不成立」として残し、受付要求IDで後から確認できるようにしている。

### 5.2 取消し

管理者だけが行える。ロックの中で予約を「取消済み」にし、駐車枠を「解放」して、操作履歴に操作者・理由を残す。

### 5.3 通知

- 確定処理とは分離している。5分ごとの時間主導トリガー `job_processNotifications` で送る。
- 送る対象を「送信中」にしてからロックの外でメールを送り、結果を「送信済み」か「再送待ち」として記録する。
- メールの失敗や1日の送信上限で、予約を変えることはない。再送待ちは次回に送る。
- 送信中のまま10分止まった分は、再送待ちに戻す。
- メールの無い電話受付は「電話連絡」として、管理者の一覧に出る。

## 6. 台帳（スプレッドシート）

見出しは日本語。文字列はアポストロフィ付きで書き込み、日付・数値への自動変換（電話番号の先頭0が消える等）を防いでいる。

| シート | 単位 | 主な列 |
|---|---|---|
| 予約 | 予約1件 | 予約番号、受付要求ID、状態（受付中／確定／不成立／取消済み）、受付経路（ONLINE／PHONE／COUNTER）、利用日、コマID、時間帯、台数、料金合計、開始日時、終了日時、氏名、棟、部屋番号、電話番号、メール、連絡方法、受付日時、確定日時、更新日時、登録者、不成立理由、電話等の受付日時、備考 |
| 割当て | 駐車枠1つ | 予約番号、利用日、コマID、駐車場、状態（有効／解放）、確保日時 |
| 通知 | 予約1件 | 予約番号、状態（未送信／送信中／送信済み／再送待ち／電話連絡／電話連絡済み／不要）、送信先、試行回数、最終結果、更新日時、電話対応者、電話対応日時 |
| 操作履歴 | 操作1件 | 日時、操作（代行登録／取消し／電話連絡済み）、操作者、予約番号、理由、内容 |

ハーネスは、試験のたびにこの台帳を実装のコードを通さずに直接読み、次の不変条件を確かめている。
- 同じ日・コマ・駐車場に有効な割当てが2つ無い
- 確定予約の台数と有効な割当ての数が一致する
- 取消済みの予約が枠を持たない
- 受付要求IDが重複しない
- 年を含む日付である

## 7. サーバーの関数と権限

名前が `_` で終わらない最上位関数は誰でも呼べるため、すべて権限区分を宣言し、管理者用・運用用はサーバー側で確認している。

| 関数 | 区分 | 内容 |
|---|---|---|
| `doGet` | 公開 | 画面を返す（`?page=admin` で管理者画面） |
| `api_getAvailability` | 公開 | 期間（最大62日）の空き状況。個人情報は返さない |
| `api_submitReservation` | 公開 | オンライン申込み |
| `api_getRequestStatus` | 公開 | 受付要求IDで結果を確認する |
| `api_lookupReservation` | 公開 | 予約番号と電話番号の下4けたで自分の予約を確認する |
| `api_admin_login` | 管理者 | 管理者の確認。トークンを発行する |
| `api_admin_register` / `api_admin_list` / `api_admin_cancel` / `api_admin_callList` / `api_admin_markCalled` | 管理者 | 代行登録・一覧・取消し・電話連絡 |
| `job_processNotifications` | ジョブ | 通知の送信（所有者の実行だけ受け付ける） |
| `setup_run` / `setup_init` | 運用 | 初期設定（所有者の実行だけ受け付ける） |

### 管理者の確認方式（仮）

- 管理者メールアドレスと管理者パスコード（8文字以上）で確認する。
- パスコードは塩付き SHA-256 ハッシュだけを保存し、平文は残さない。
- 確認できたら6時間有効な印（トークン）を発行する。
- 5回間違えると15分止まる。
- 画面の切替や URL を知っているだけでは、管理者になれない。

## 9. 検証の結果

Google に接続できない環境のため、GAS とスプレッドシートの挙動を再現するハーネスで検証した。

### 9.1 ハーネスの再現範囲

- 各実行を別スレッドで並行させ、シート操作ごとに遅延を入れて競合の隙間を広げる。
- 書込みは flush まで他の実行から見えない場合がある、という最悪の場合を再現する。
- 文字列の自動変換、戻り値の Date が null になる挙動、末尾 `_` の関数、公開設定による利用者情報の違い、ロックのタイムアウトを再現する。

### 9.2 最終結果（`npm run verify:strict`：合格、2026-10-19 画面の作り直し後）

| 関門 | 結果 |
|---|---|
| 保護ファイルの改変なし | 合格 |
| GAS 静的検査 | エラー 0、注意 0 |
| エミュレータの前提 | 18 / 18 |
| 受入試験 | 35 / 35（同時申込み・管理者登録との競合・古い画面・再送・連打・通信断・書込み失敗・途中停止・ロック失敗・通知失敗・メール上限・権限・個人情報・監査・境界値） |
| 画面試験 | 13 / 13（UI-01〜UI-11。PC 幅の試験を含む） |
| 画面の自動監査 | iPhone SE・Pixel 7・PC（1280px）の利用者・管理者画面で合格 |
| ペルソナ評価（実行ID r9） | 6人全員合格（下表）。ただし、その後の見た目の作り直し（D-013）は評価していない（利用者の指示） |

ハーネス自体の自己試験も合格した（わざと壊した実装14種をすべて検出）。

改善の経過（作り直し後）：
- r5：評価役どうしのセッション取り違えが見つかり、合否に使わなかった（HX-006）。指摘から、満車が行き止まり、スマホで予約番号が下に隠れる、電話で伝えた予約まで「電話連絡」に数える、を直した。

- r8：作り直しで生じた、管理者のスマホ画面の横はみ出しが見つかり、直した（画面試験にも加えた）。
- r9：全員合格。致命的・重めの不満は0件。

|---|---|
| 申込み1件のシート操作 | 15回（推定 約1.2秒） |
| 1か月分の空き表示 | シート操作4回（推定 約0.3秒） |
| 同時10件の申込みのロック待ち | 最大 約1.4秒、中央値 約0.8秒（エミュレータ上） |

推定値は仮の単価によるもので、実環境プローブで校正する必要がある。

## 10. 残っている課題と注意点

### 人の判断が必要なこと

1. 運用ルールの正式決定（3章。特に、先着順の正式採用と、先着の基準）。
2. 管理者の確認方式（パスコードのままか、Google アカウントにするか）と、住民に Google ログインを求めるか。
3. 利用者自身による取消し・変更の方法（U-09）と、本人確認の方法。
4. 特別予約（A-10）、全日予約の扱い。
5. 性能の合格基準（`contract/perf-budget.json`）。

### 本番前に必ず行うこと（`docs/REAL_ENV_CHECKLIST.md`）

1. **実環境プローブ**：エミュレータの仮定（`harness/real-gas/ASSUMPTIONS.md` の約30項目、多くは未確認）が本物の GAS と一致するかを確かめる。特に次の3つ。
   - 文字列の自動変換
   - flush とロックの関係
   - 公開設定と利用者情報の関係
2. 実機（iPhone・Android）での操作と、2台同時の申込み。
3. 実際の住民・管理者による使い勝手の確認。ペルソナ評価はAIによる予測なので、人で裏づける。

### 分かっている弱点

- 入力欄（お名前・棟・部屋・電話・メール）の数が手数の大半を占める（通勤中の親：上限12手に対して10手）。2回目からは前回の入力が残る。
- 最初の画面は今日からの7日分のため、翌週の予約には「次の週」を1回押す。
- 画面の自動監査は、管理者画面を確認前の画面でしか測っていない（DECISIONS「ハーネスへの指摘」）。
- 通知処理が送信中に止まると、まれに同じメールが2通届く可能性がある（届かないよりよいと判断）。
- パスコードの忘失時は、運用担当者が再設定する必要がある。
