自治会駐車場予約システム

基本実装に向けた要件定義・開発引継ぎ

更新日：2026年10月19日
位置付け：基本実装のための要件案。本番運用の詳細ルールには未確定事項がある。

1．目的

自治会の駐車場予約を、住民と非エンジニアの管理者が分かりやすく利用できる仕組みにする。

オンラインからの申込みに加え、電話・対面などのアナログ受付を併用する。アナログで受け付けた内容は、管理者がスマートフォンなどからその都度登録する想定である。

受付経路にかかわらず、予約情報を共通の台帳で管理し、二重予約や受付漏れを防ぐ。

2．決定事項・方針・未確定事項

区分	内容
決定	オンライン受付とアナログ受付を併用する
決定	利用者・管理者の双方に分かりやすいUIを用意する
決定	カレンダーなどを用いて予約状況を確認しやすくする
決定	管理者が扱う予約台帳が必要
有力な方針	GASを中心に、HTMLの画面とスプレッドシートを組み合わせて構築する
想定する運用	電話・対面で受けた申込みを、管理者がその都度入力する
未確定	抽選方式を廃止し、先着順へ移行するか
未確定	先着順の場合、何をもって受付順とするか
未確定	本人確認、管理者認証、取消し・変更・特別予約などの詳細ルール

GASによるUIの本格利用と、先着順の正式採用は別の事項として扱うこと。

3．開発上の基本方針

* 既存のGoogleフォームへ機能を継ぎ足すことに固執せず、GASのHTML画面を中心に構成する。
* オンライン予約と管理者の代行登録は、同じ予約台帳・空き判定・確定処理を使う。
* 管理者が日常業務でスプレッドシートのセルを直接編集する必要がない構成にする。
* まず基本操作を実装し、利用者と管理者が実際に試せる状態を作る。
* 未確定の運用ルールは、仮ルールであることを明記し、設定または処理の差し替えで変更できるようにする。
* 既存の抽選版、過去の試験記録、現在のデモを無断で上書きしない。

4．利用者と役割

役割	主な操作
一般利用者	空き状況の確認、申込み、予約結果の確認、許可された範囲での取消し・変更
管理者	電話・対面受付の代行登録、予約台帳の確認、取消し・変更、連絡状況の記録
運用担当者	設定、公開、障害対応、バックアップ、管理者の追加・削除

管理者は非エンジニアを想定する。スマートフォンから短い操作で登録できることを重視する。

5．駐車場・時間帯・料金

項目	内容
駐車場	91・92・93の３台分
第１コマ	8:00〜11:00、300円／台
第２コマ	11:00〜14:00、300円／台
第３コマ	14:00〜17:00、300円／台
第４コマ	17:00〜翌8:00、600円／台
共有範囲	各棟で共通の駐車枠を利用する
全日指定	要望はあるが、時間範囲・料金・割当て方法は未確定

日時は日本時間で扱う。第４コマの終了日は翌日になることを、表示・判定・台帳で一貫させる。

6．機能要件

6.1 利用者向け画面

ID	要件
U-01	カレンダーから利用日を選択できる
U-02	日付ごとの空き状況を把握できる
U-03	選択日の各コマについて、時間帯・料金と、空きがあるかどうかを確認できる（残り台数は住民に見せない。管理者は確認できる）
U-04	希望するコマと必要情報を入力して申し込める
U-05	送信前に、日付・時間・料金などの内容を確認できる
U-06	受付のみの状態と、予約確定の状態を明確に区別する
U-07	成立・不成立・処理中・通信エラーを分かりやすく表示する
U-08	予約番号を表示し、予約内容を後から確認する方法を用意する
U-09	取消し・変更は、決定された運用ルールと本人確認方法に従って行う

カレンダーは、月表示だけにこだわらない。スマートフォンでは「日付選択＋当日のコマ一覧」など、操作しやすい表示も用意する。

一般利用者向けの画面には、他人の氏名・部屋番号・連絡先を表示しない。

6.2 管理者向け画面

ID	要件
A-01	スマートフォンで空き状況と予約一覧を確認できる
A-02	電話・対面で受け付けた予約を代行登録できる
A-03	登録時に、利用者・日付・コマ・台数・連絡方法を確認できる
A-04	一般利用者と同じ台帳を使い、競合する予約を確定させない
A-05	日付・駐車場・棟・部屋・予約番号などから予約を探せる
A-06	予約の取消し・変更ができる
A-07	電話連絡が必要な予約と、その対応状況を確認できる
A-08	誰が登録・変更・取消しを行ったかを記録する
A-09	必要に応じて、その日の予約一覧を印刷・出力できる
A-10	特別予約の機能は、一般の代行登録とは区別する

従来の管理者フォームには「１台＝91、２台＝91・92、３台＝全枠」という指定があった。ただし、通常の電話予約の代行入力にも同じ指定を適用するかは未確定である。

6.3 アナログ受付との連携

基本案は以下とする。

1. 管理者が電話・対面で申込みを受ける。
2. 管理者画面で空き状況を確認する。
3. 共通の予約処理で枠を確保する。
4. 確定結果を見て利用者へ伝える。
5. 必要に応じて紙へ控えを残す。

紙と電子で独立した確定台帳を作らない。

紙へ記録して後日まとめて登録する運用が必要になった場合は、優先順位や枠の仮確保などを別途設計する。過去の受付時刻を入力するだけで、確定済みのオンライン予約を自動的に取り消す実装にはしない。

6.4 予約台帳

回答の記録と、実際に確保された駐車枠を区別する。

台帳には、少なくとも以下を保存する。

分類	項目
識別	予約ID、受付要求ID
利用日時	利用日、コマID、開始日時、終了日時
割当て	駐車場番号、台数
利用者	氏名、棟、部屋番号、必要な連絡先
受付	オンライン・電話・対面・管理者特別予約などの経路
時刻	システム受付日時、確定日時、更新日時、必要なら電話等の受付日時
状態	受付済み・確定・不成立・取消済みなど
金額	適用料金、計算に使った料金区分
連絡	連絡方法、通知状況、対応済み日時
管理	操作者、変更理由、備考

日付は年を含めて保存する。棟やコマの表示名を識別キーにしない。

6.5 予約確定と競合処理

* 空き状況の表示だけで確定を判断しない。
* 確定処理の直前に、最新の予約情報を読み直す。
* 空き確認から枠の記録までを、共通の排他制御の対象にする。
* 管理者からの登録も、同じ制御を通す。
* 同じ受付要求が再送されても、重複登録しない。
* 処理できなかった場合、成功したように表示しない。
* 通信が切れた場合、受付要求IDなどから結果を再確認できるようにする。
* 複数台の予約は、一部だけ確定するのか、全部そろう場合のみ確定するのかを明確にする。

先着順を採用する場合は、「申込み時刻順」と「枠を確保できた順」を混同しない。厳密な受付順が必要なら、受付順序を管理する仕組みを設ける。

6.6 通知

* 予約の確定処理と、メールなどの通知処理を分離する。
* 通知失敗を理由に予約を取り直したり、再抽選したりしない。
* 未通知・通知失敗・再送対象を管理者が把握できるようにする。
* アナログ受付では、メールがなくても登録できる必要がある。
* 電話連絡の場合は、担当者が対応したことを記録できるようにする。

メールアドレスをオンライン利用者の必須項目にするかは、改めて確定する。従来フォームでは必須だったが、その条件をアナログ代行登録へそのまま適用しない。

7．技術要件

7.1 構成案

層	採用候補・方針
画面	GASのHTML ServiceによるWebアプリ
クライアント	HTML・CSS・JavaScript
サーバー処理	Google Apps Script
保存先	Googleスプレッドシート
排他制御	同一GASプロジェクト内の共通ロック
通知	GASからのメール送信など。予約処理から分離する
時刻	日本時間を基準とし、保存・表示の形式を統一する

7.2 実装上の要件

* 公開Webアプリの処理は、アクティブなスプレッドシートに依存させず、設定したIDから開く。
* 入力値は、画面側だけでなくGAS側でも検証する。
* コマは S1〜S4 などの固定IDで管理する。
* 料金はコマ名の文字列一致から切り離す。
* 回答・予約台帳・通知記録・操作記録・設定を、役割に応じて整理する。
* 処理対象のシートは明示的に指定する。
* 日常運用での直接セル編集を避け、変更は共通処理を通す。
* 本番・検証・デモの保存先と設定を分ける。
* 初期設定・公開・更新・復旧の手順を文書化する。
* ソースの版と実行環境を識別できるようにする。固定の文字列を「現在実行中のコードのハッシュ」として扱わない。

7.3 データ構造の基本案

保存領域	役割
予約台帳	予約単位の申込者・状態・受付経路など
駐車枠の割当て	予約IDと、確保した日時・コマ・駐車場の対応
通知記録	送信対象、状態、試行回数、最終結果
操作履歴	登録・変更・取消し・操作者・理由
設定	駐車場、コマ、料金、予約期間、運用ルール

必要以上にシートを増やさない。複数台や全日を扱う場合でも、同じ情報を複数箇所へ独立して保存し、不整合が生じる構造にしない。

8．非機能要件

分類	要件
操作性	非エンジニアが説明を読み込まずに基本操作を行える
スマートフォン対応	横スクロールに依存せず、日付選択・登録・取消しを行える
表示	空き・満車・確定・未確定を、色だけでなく文字でも示す
性能	空き表示、受付、確定、通知の所要時間を個別に測定できる
安定性	同時申込み、再送、処理途中の失敗で重複や受付漏れを起こさない
復旧性	中断した予約・通知の状態を把握し、安全に再開できる
整合性	利用者画面、管理者画面、台帳で同じ確定情報を参照する
セキュリティ	管理者操作をサーバー側で認可する。画面の切替だけを認証にしない
個人情報保護	一般公開の空き画面へ、氏名・部屋・連絡先を返さない
監査性	管理者が誰の予約をどう変更したか追跡できる
保守性	料金・コマ・予約期間などを変更しやすくする
継続運用	担当者交代時の所有権、権限、公開方法、バックアップを引き継げる
費用・制限	GASやメールの利用上限を考慮し、超過時に未処理を把握できる

具体的な応答時間や想定同時利用人数は未確定。最初から根拠のない保証値を置かず、初期実装で測定して合格基準を決める。

ただし、重複確定・受付済み申込みの所在不明・無断の結果変更については、０件を目標とする。

9．権限と公開範囲

本番では、次の区別が必要。

対象	扱い
空き状況	個人情報を含まない情報として公開を検討
一般利用者の予約確認・取消し	本人だけが操作できる仕組みが必要
管理者の台帳閲覧・代行登録	管理者認証とサーバー側の権限確認が必要
台帳そのもの	一般公開しない

一般利用者にGoogleログインを求めるか、予約確認用の別の方法を用意するかは未確定。

管理者のGoogleアカウントを使う場合も、公開設定とGASが取得できる利用者情報を確認してから実装する。管理者用URLを知っているだけで操作できる設計にはしない。

11．試験要件

正常動作

* 利用者と管理者が同じ空き状況を参照する。
* オンラインと電話代行登録が同じ台帳へ入る。
* 取消し後に、対象の枠が正しく空きに戻る。
* 第４コマの翌日終了と料金が正しい。

競合・境界・障害

* 残り１台へ、複数の利用者が同時に申し込む。
* 利用者の申込みと管理者登録が重なる。
* 古い空き画面から申し込む。
* 確定処理中に通信が切れ、同じ内容を再送する。
* 取消しと新規予約が重なる。
* ロック取得に失敗する。
* 通知だけが失敗する。
* 受付期限の直前・直後に申し込む。
* 複数台のうち一部の枠だけが埋まっている。

測定する時間

指標	測定範囲
空き表示時間	画面の要求から、空き一覧の表示まで
受付待ち時間	システム受付から、処理開始まで
ロック待ち時間	ロック取得要求から、取得まで
確定処理時間	処理開始から、確定情報の保存まで
利用者の待ち時間	送信操作から、画面で結果を確認できるまで
通知時間	確定情報の保存から、通知処理の完了まで

実メールの配送・受信時間と、GASの送信処理完了時間は区別する。

件数を増やすだけの試験に偏らず、処理が重なった際の正確さを優先する。

13．実装前に確認する運用ルール

基本画面の作成は進めてよいが、以下は本番確定処理を仕上げる前に決める。

確認事項	判断が必要な内容
予約方式	先着順・抽選・併用
先着の基準	送信時刻、システム受付順、枠の確保順など
アナログ受付	その場で登録できるか、後から登録する場面があるか
予約期間	何日前から、いつまで申し込めるか
当日予約	許可するか。コマ開始後はどうするか
重複・上限	同じ世帯で何件・何台まで予約できるか
取消し・変更	誰が、いつまで、どの方法で行うか
特別予約	一般予約との優先順位、理由、承認の要否
全日	対象時間・料金・同じ駐車場を継続利用する必要
本人確認	住民と管理者をどのように確認するか
連絡方法	メール必須の範囲、電話への振分け
障害時	電子台帳を使えない間に受付・確定をどう扱うか

14．実装担当AIへの指示

GASとHTMLを使い、スマートフォンで操作できる自治会の駐車場予約システムを基本実装してください。

利用者のオンライン予約と、管理者による電話・対面受付の代行登録を、共通の台帳・空き判定・予約確定処理へ統合してください。カレンダーとコマ一覧から空きを把握できるUIを重視してください。

既存デモは参考にできますが、管理者認証などがないため、そのまま本番用として扱わないでください。旧抽選版の重複予約や通知復旧の問題を持ち込まないでください。

未確定の運用ルールを勝手に本番仕様として確定せず、仮設定と未決定事項を明記してください。まず変更しやすい基本画面と共通予約処理を実装してください。

検証では大量件数だけでなく、残り１枠への競合、管理者登録との競合、再送、取消し、通信断、通知失敗を重視してください。受付・待機・確定・通知の時間を分けて測定できるようにしてください。
