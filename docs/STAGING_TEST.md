# 別アカウントでのプレ解禁テスト（実機・residentBooking を有効にして実施）

作成: レビュー担当（2026-11-13）。決定の記録: docs/DECISIONS.md D-046。
目的: **本番（本物の自治会アカウント）では住民の予約（residentBooking）をoffのまま**にし、**別のテスト用アカウント**で予約をonにして、実機での最終確認と限度の測定を済ませる。本番の無料 quota を攻撃系の試験で消費しないため、破壊系はすべてこのテスト環境だけで行う。

## 0. 2つのアカウントの役割

| | 本番（本物の自治会用アカウント） | テスト（別のGoogleアカウント1つで作る） |
|---|---|---|
| residentBooking | **false（T系列と審査が終わるまで）** | **true（最初から）** |
| 台帳シート | 本物の台帳。予約は電話で受付 | 作り直しのdummy（A棟101 などの試験用の部屋）。実際の住民の氏名・連絡先は書かない |
| Pages の画面 | 本番のプロジェクト（QR はこっちへ向ける。テスト中は入口まだ作らない） | **別のプロジェクト**（例 `xxx-parking-test.pages.dev`。本番に手を触れない） |
| 何をする | 板員だけが管理者画面を実運用（代行・取消し・変更・使用禁止） | 予約onの全流れ＋同時実行・大量申込などの限度測定 |

## 1. テスト環境を立ち上げる（今からやること。だいたい1時間）

1. 新しいGoogleアカウントを作る（テスト専用。個人メインのアカウントは使わない）
2. そのアカウントでスプレッドシートを1枚作る（名「駐車場予約（テスト）」）。列は作らない（`setup_init` が作る）
3. リポジトリと同じ `src/` で Apps Script プロジェクトを作る（`docs/SETUP.md` の 1〜3章と同じ手順）
4. スクリプト プロパティ（`docs/SETUP.md` 2章）。テスト用の値:
   - `RULES`: `residentBooking: true`、`residentLeadDays: 0`（当日・翌日にすぐ予約して検証するため。本番は 5）、`residentViewMonths: 2`、`capacityPerSlot: 2`、`remindHour: 17`、`adminLockout: false`、相談先・受付時間・利用約款はダミーの文
   - `ADMINS`: 試験用の管理者1〜2人（試験用パスコード。16文字以上）
   - `SPREADSHEET_ID`: 2. のシート
5. `setup_init` → `setup_run` を1回ずつ実行。トリガー画面に `job_processNotifications`（毎日、remindHour）と `job_archiveLedger`（毎深夜）が出ることを確認
6. 管理者画面（`?page=admin`）でログインし、dummy の部屋（A棟101、B棟202 など架空のものだけ）で電話予約を数本入れて板員操作に習熟
7. 外に置く画面を作る（テストの GAS URL へ向ける）:
   `node tools/build-static.js --gas "https://script.google.com/macros/s/テスト/exec" --fallback "テスト事務局（電話 000-0000-0000）"`
   → Cloudflare Pages に**別のプロジェクト**として置く（`docs/STATIC_PAGES.md` §3）

## 2. テストの流れ（この順。チェック表にし、結果はこの下に書く）

### 段A: 最後の確認（普通に使ってみる。攻撃なし）
- [ ] **T18（最重要・初めに）**: Google に複数アカウントでログインした実スマホで Pages のテストURLを開く → 空き（○×）が出る・「ファイルを開くことができません」が出ない・予約1本が成立する。**ここで通信が止まったら、入口の設計判断（Pages か GAS か）をここで決める**（GAS の 302 越しにブラウザの fetch が通るかの未実測点。`docs/STATIC_PAGES.md` 末章）
- [ ] 予約 → 確定の画面が即出る → 「結果を確かめる」で同じ結果 → 取消し → 空きに戻る
- [ ] 管理者の代行登録・変更・取消し・使用禁止がシートに反映される
- [ ] **前日の案内のメール**: 翌日分の予約を入れ、`remindHour` を1時間後に一時的に変えて `setup_run` をもう一度（トリガーが作り直される。SETUP 4章）→ 指定時刻に**本物のメールボックスへ1通だけ**届くのを確認。戻す（17時）
- [ ] 保管: 過去のdummyの行が `job_archiveLedger`（手動実行でよい）で保管シートへ移る
- [ ] T01〜T08・T17（`docs/REAL_ENV_CHECKLIST.md` の本番前提の項目）
### 段B: 板員の実運用リハーサル（1週間）
- [ ] 板員だけで管理者画面を毎日使う（電話受付の実運用と同等）。操作待ち・見間違い・取り消しの事故が起きないか
### 段C: 限度の実測（**このテスト環境だけで**。本番では絶対にやらない）
- [ ] 解禁日まね: 架空の身分で **50本を同時**に申込（手ならブラウザを10人で同時押し。機械は実装item P-11 の負荷試験の用意を待つ）→ **BUSY（混み合って処理できませんでした）の回数**と応答の待ち時間を測る
- [ ] **1本の申込の実行時間**（Apps Script の実行ログ `console.log` の ms と、体感）→ `withLock_` の待ち15秒を短くするかの決定（D-043・P-5）と cost-model の再校正（P-8）に使う
- [ ] ゴミ申込の連発（期間外・過去日・連続超過）→ **応答は即返る・シートに行が増えない**（G2 の実機確認）。満車狙いはロックを取る（U-07 の約束）ので、BUSY が出るまでの数を測る
- [ ] quota の消費を見る（Apps Script ダッシュボードの実行分・メール数）→ 無料の90分/日・100通/日に対して本番想定の規模（世帯数×4コマ/月）に十分余裕があるか
### 判定（解禁を止める線）
| 結果 | 行動 |
|---|---|
| 50同時に BUSY ほぼゼロ・応答数秒 | そのまま解禁へ。15秒の待ちは変えない |
| 50同時に BUSY が出る | 実測1本分のmsを見て `withLock_` の待ちを短縮（実装担当の作業・T09/T15の実測値を添えて判断） |
| Pages→GAS の fetch が止まる | 入口を GAS 画面へ戻す（コード変更なし。QRだけ刷り直し） |
| 案内のメールが 1通届かない/重複 | 解禁を見合わせ、`job_processNotifications` の実行ログとトリガー時刻を調査 |
| ○×と実際の空きが食い違う | **解禁中止**。台帳の実物と突き合わせて原因調査 |

## 3. 合格後の本番への橋渡し

1. 本番アカウントで `RULES` を本番値に（`residentBooking: false`、`residentLeadDays: 5`、実在の相談先・約款・電話）
2. 本番の GAS URL で画面を作り直し、**本番の Pages プロジェクト**へ（STATIC_PAGES §2〜3）
3. **T18 を本番でも**（テストアカウントと本番アカウントで Google の挙動が違うことがある）
4. 板員のみで管理者運用を確認 → QR を配る → **解禁**（`residentBooking: true`。leadDays 5 で最初の1週間が天然の緩衝材）
5. 問題が出たら `residentBooking: false` の1行だけで電話受付へ戻れる（緊急停止の手順を板員に共有しておく）
